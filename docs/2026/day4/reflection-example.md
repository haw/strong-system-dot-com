# Day 4 振り返りの例

[Day 4 のハンズオン](./)の手順6で書く、振り返りの例です。時刻は例です。自分のメモの時刻に置き換えて読んでください。

## 何分でアラームが鳴ったか

**例：** 10時00分にルールを消し、10時03分に ALARM になった。気付くまで約3分。

アラームが鳴るまでには、次のことが順に起きています。

1. cron が、次の1分ごとのアクセスでアプリケーションを呼ぶ。ルールを消した直後なら、最大1分待つ。
2. アプリケーションが DB への接続を待ち、失敗して `Error` の行をログに出す。接続を待つ時間が加わる。
3. ログが CloudWatch Logs に届き、メトリクスフィルターが `AppErrors` を数える。
4. アラームが、期間1分の合計を見て、しきい値を超えたと判断する。

**もっと早く気付くには：** 今回の設定（期間1分、1つ中1つ）は、すでに短いほうです。さらに早くするなら、利用者や cron のアクセスを待たずに、外から定期的に確かめるしくみ（事前学習6.4の CloudWatch Synthetics）を足す方法があります。

ただし、早く鳴らすほど、一瞬のエラーでも鳴りやすくなります。鳴りすぎると、通知に慣れて本当の異常を見逃します（事前学習6.1）。どこまで早く気付く必要があるかと、鳴りすぎない設定とのバランスで決めます。

## 障害のあいだ、CPU と RDS の状態はどう見えていたか

**例：** EC2 の CPU 使用率は、障害の前とほとんど変わらず低いままだった。RDS の状態は「利用可能」のままだった。

DB へ届かない障害では、EC2 も RDS も「元気」に見えます。CPU や RDS の状態だけを見張っていたら、気付けませんでした。利用者に見える症状（アプリケーションのエラー）を見張る理由です（事前学習1.2、2.1）。

## アラームが鳴ったとき、最初に何を見ればよいか

**例：** アラームの説明に「アプリのDB接続エラー。まずロググループ /day3-2026/tanaka/app を見る」と書いておいた。ロググループを開くと `ETIMEDOUT` が並んでいて、DB まで届いていないと分かった。ここまでは説明で足りた。

足りなかったこと、足すとよいことの例：

- エラーの種類ごとに、次に見る場所を書く。`ETIMEDOUT` なら RDS のセキュリティグループ、`Access denied` なら DB のユーザーとパスワード（Day 3 の切り分け）。
- 最初に開くダッシュボードの名前を書く（追加課題2）。
- 鳴ったときに、誰に連絡するかを書く。

説明は、鳴ったときに初めて読む人が、すぐに動けることを目指します（事前学習6.3）。
