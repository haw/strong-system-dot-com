# Day 3: ヒントと答え

[Day 3 のハンズオン](./)で詰まったときに見るページです。

いま画面やログに出ているエラーの節を開いてください。まずヒントだけを読み、自分で確かめてみます。それでも分からなければ、「答えを見る」を開きます。答えを見て直したときも、**なぜそうなっていたのか**を、ヒントの確かめ方で一度確かめてください。

直したら、ハンズオンの 4-3 のとおりアプリケーションを起動し直し、ブラウザを再読み込みします。エラーが変わったら、1つ前進です。次のエラーの節に進みます。

---

## `ENOTFOUND` が出ている

**ヒント**

- 止まっている段階は「名前を引く」です。アプリケーションは、接続先の名前から IP アドレスを引けていません。
- アプリケーションのログの最初の行（`DB_SOURCE=ssm host=...`）に、アプリケーションが使っている接続先が出ています。
- その `host=` の値と、**Aurora and RDS** の「接続とセキュリティ」タブにあるエンドポイントを、1文字ずつ比べてみてください。

<details markdown="1">
<summary>答えを見る</summary>

**原因：** Parameter Store の `/day3-2026/{あなたの名前}/db/host` が、本当のエンドポイントと1か所だけ違っています。`-db-` が `-bd-` になっていて、存在しない名前なので引けません。

**根拠：** ログの `host=` と、RDS のコンソールのエンドポイントが一致しない。`getent hosts "$DB_HOST"` で、本当のエンドポイントは引けるのに、ログに出ている名前は引けない。

**直し方：**

1. **Systems Manager** の「パラメータストア」で `/day3-2026/{あなたの名前}/db/host` を開き、「編集」を選ぶ。
2. 「値」を、RDS のコンソールからコピーしたエンドポイントに置き換え、「変更を保存」を選ぶ。
3. ハンズオンの 4-3 のとおり、アプリケーションを起動し直す。

**直ったときの見え方：** `ENOTFOUND` は消えます。代わりに、しばらく待たされてから別のエラーが出たら、次の節に進みます。

</details>

---

## `ETIMEDOUT` が出ている（しばらく待たされてから失敗する）

**ヒント**

- 止まっている段階は「通信を始める」です。名前は引けていますが、RDS の 3306 番ポートまで届いていません。
- `timeout 5 bash -c "</dev/tcp/$DB_HOST/3306"` で、5秒待たされてから `届かない` になるかを確かめます。待たされるのは、途中で通信が捨てられているときです。
- 通信を止めるのは、まずセキュリティグループです。RDS 側の `day3-2026-rds-sg-{あなたの名前}` の「インバウンドルール」に、アプリケーションからの 3306 を許可するルールがあるかを見ます。

<details markdown="1">
<summary>答えを見る</summary>

**原因：** RDS のセキュリティグループから、アプリケーションのセキュリティグループ（`day3-2026-app-sg-{あなたの名前}`）からの 3306 を許可するルールが消されています。

**根拠：** `/dev/tcp` で5秒待たされて `届かない`。RDS のセキュリティグループのインバウンドルールが空。

**直し方：**

1. **EC2** の「セキュリティグループ」で `day3-2026-rds-sg-{あなたの名前}` を選ぶ。
2. 「インバウンドルール」タブ →「インバウンドのルールを編集」→「ルールを追加」を選ぶ。
3. タイプ「MYSQL/Aurora」（ポート3306）、ソース「カスタム」で `day3-2026-app-sg-{あなたの名前}` を選び、「ルールを保存」を選ぶ。
4. ハンズオンの 4-3 のとおり、アプリケーションを起動し直す。

ソースを `0.0.0.0/0` にしてはいけません。つながりはしますが、DB に誰でも接続を試せる状態になります。許可するのは、アプリケーションのセキュリティグループだけです。

**直ったときの見え方：** 待たされなくなります。すぐに別のエラーが出たら、次の節に進みます。

</details>

## `Access denied for user` が出ている

**ヒント**

- 止まっている段階は「ログインする」です。RDS までは届いていて、ログインで断られています。待たされず、すぐに失敗するのが特徴です。
- ハンズオンの ⑥ の `docker run ... mysql` で、研修用パスワードを使ってログインしてみます。ログインできるなら、RDS は正常です。違っているのは、アプリケーションが使っているパスワードのほうです。
- これは DB のログインのエラーです。AWS の権限（IAM）のエラーではありません。IAM ロールを変えても直りません。

<details markdown="1">
<summary>答えを見る</summary>

**原因：** Parameter Store の `/day3-2026/{あなたの名前}/db/password` が、研修用パスワードと最後の1文字だけ違っています。小文字の `x` が、大文字の `X` になっています。

**根拠：** `docker run ... mysql` では、研修用パスワードでログインできる。パラメータストアで `password` の値を「表示」すると、研修用パスワードと一致しない。

**直し方：**

1. **Systems Manager** の「パラメータストア」で `/day3-2026/{あなたの名前}/db/password` を開き、「編集」を選ぶ。
2. 「値」を研修用パスワード `Tr41n-Rds2026-Kq7mZx` に置き換え、「変更を保存」を選ぶ。種類（SecureString）と KMS キーは変えません。
3. ハンズオンの 4-3 のとおり、アプリケーションを起動し直す。

**直ったときの見え方：** 画面上部の「接続先」が水色の **Amazon RDS** になり、社員一覧が表示されます。ハンズオンの手順5に進みます。

</details>

## 追加の障害：セキュリティグループは正しいのに `ETIMEDOUT` が出る

講師に追加の障害を入れてもらった人向けです。

**ヒント**

- セキュリティグループのほかにも、通信を止めるものがあります。サブネットの出入り口にある「ネットワークACL」です。
- **VPC** の「ネットワーク ACL」で、`day3-2026-vpc-{あなたの名前}` のネットワークACLを選び、「インバウンドルール」を見ます。
- ネットワークACLのルールは、ルール番号の小さい順に評価され、最初に一致したルールが使われます。

<details markdown="1">
<summary>答えを見る</summary>

**原因：** ネットワークACLに、ルール番号 50 で「10.0.0.0/16 からの TCP 3306 を拒否」が足されています。番号 100 の「すべて許可」より先に評価されるので、セキュリティグループが正しくても止まります。

**根拠：** セキュリティグループは正しいのに、`/dev/tcp` で5秒待たされて `届かない`。ネットワークACLのインバウンドルールに、3306 を拒否するルール 50 がある。

**直し方：**

1. **VPC** の「ネットワーク ACL」で、自分の VPC のネットワークACLを選ぶ。
2. 「インバウンドルール」タブ →「インバウンドルールを編集」を選ぶ。
3. ルール番号 50 の行を「削除」し、「変更を保存」を選ぶ。
4. ハンズオンの 4-3 のとおり、アプリケーションを起動し直す。

**直ったときの見え方：** 「接続先」が水色の **Amazon RDS** に戻り、社員一覧が表示されます。

</details>
